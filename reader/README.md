# Диагностика HUD

## Запуск после клонирования

Это исходники рабочего ридера, пока без готового установщика. Нужен Windows и Python с Tkinter.
Из корня репозитория:

```powershell
py -3 -m venv reader/.venv
reader/.venv/Scripts/python.exe -m pip install -r reader/requirements.txt
```

Установи аддон, настрой HUD и сохрани собственный `/ahw export` как
`reader/profile.json` (JSON в UTF-8). Затем запусти `reader/Start.vbs`.
Назначения клавиш нужно настроить самостоятельно. Чтение начинается кнопкой
«Начать», остановка — F8. Личные профили, назначения и логи исключены из Git.
Сохранённые `docs/arms-apl/build.txt` и `decoded-build.json` также локальные:
для повторного декодирования потребуется собственная строка талантов.

Ниже сохранены заметки разработки; упоминания локальных профилей и записей
боя не означают, что эти файлы входят в репозиторий.

## Основное окно настроек — 0.2.13

Кнопка у миникарты и `/ahw config` открывают настройки вида, закрепления/положения, иконок, превью и экспорт для ридера. Ручной редактор перенесён в раскрываемый раздел «Диагностика»; прямой доступ — `/ahw editor`. Он сохраняет прежние наборы и возможности редактирования. Настройки закрываются при входе в бой.

Это изменение навигации: автоматическая генерация всех наборов из SimulationCraft APL пока не реализована. Текущий набор и назначения клавиш сохранены. После установки нужен `/reload`; один лишь перенос меню не меняет координаты HUD. Изменение компактности, положения или превью по-прежнему требует нового экспорта. Новое окно ещё нужно визуально проверить в WoW.

## Компактный HUD — 0.2.12

Первая запись компактного режима выявила помеху чтению здоровья цели: вертикальная отметка 35% попала в прямоугольник цифр и распознавалась как лишняя `1`. Подтверждено отдельным снимком полосы. Компактные отметки 20/35 теперь короткие, у нижней границы полосы, вне области цифр. Геометрия экспорта не меняется; для исправления нужен `/reload`, затем повторная проверка чтения процента.

Вне боя: `/ahw compact on` либо кнопка «Вид» в `/ahw config`. Возврат — `/ahw compact off`. Настройки размера квадратов, масштаба и полного вида сохраняются. Раскладка не переключается в бою.

- Сетка: семь столбцов, меньшие отступы; размер квадратов, таймеров и стаков прежний.
- Для Arms здоровье игрока, ярость, здоровье цели и GCD расположены в одной строке. Размер цифр сохраняется.
- Контекст: более низкие ячейки, короткие подписи и компактная нижняя строка. Все входы APL, флаги ввода, оценка целей и история событий остаются видимыми.
- Большая легенда превью в компактном режиме скрывается; иконки и номера квадратов при включённом превью остаются. Для легенды верни полный вид.
- Экспорт содержит `display.compact`, фактические интервалы/столбцы, а также `contextNumbers` и `contextSamples`. Ридер использует указанные области цифр и свободные от текста точки цвета. Старые экспорты полного вида поддерживаются.

Порядок обновления: остановить ридер, выполнить `/reload`, вне боя включить компактный вид, сделать `/ahw export`, загрузить новый экспорт в обновлённый ридер. Старые координаты после смены вида не подходят. Назначения клавиш не меняются. Обратное переключение также требует нового экспорта.

Для текущих 27 квадратов расчётная экономия площади панели — около трети при прежнем размере цифр. Проверен синтаксис Python; визуальное расположение и распознавание новой раскладки в WoW ещё требуют проверки по скриншоту и записи боя.

## Замер ожидания после GCD

Новые события `gcd_ready_observed`, `gcd_ready_wait`, `gcd_ready_window_end` связываются полем `cycle`. Отсчёт начинается только при непрерывно наблюдаемом переходе `cd → ready`. Первоначальная готовность при запуске, переход через `unknown` и разрыв кадров больше 250 мс не считаются точным наблюдением конца GCD.

`afterReadyObservationSeconds` — время от завершения захвата первого готового кадра до отправки (либо окончания окна наблюдения). `firstReadyFrame` означает отправку при обработке этого же кадра. `hudTransitionBracketSeconds` — интервал между началом последнего занятого кадра и завершением первого готового; это неопределённость наблюдения HUD, **не измерение фактического серверного окончания GCD**. Таймер обновления аддона и рендер игры добавляют свою задержку.

Причины ожидания и их приблизительные длительности попадают в `waitSecondsByReason`; смена причины дополнительно записывает состояние «Вихря клинков» и диагностику целей. При отправке сохраняется возраст ключевых числовых наблюдений. Окна, прерванные потерей фокуса, неизвестным GCD или разрывом кадров, отмечаются отдельно. Измеритель не управляет нажатиями и не меняет APL.

Проверены синтаксис и синтетические переходы: начальная готовность, отправка в первом готовом кадре, ожидание данных и неизвестный GCD. Повторный расчёт на записи до обновления: 200 из 212 наблюдаемых окон завершились отправкой в первом готовом кадре; медиана после завершения захвата — 5,7 мс. Это офлайн-анализ существующих данных; следующий живой запуск запишет показатели напрямую. Для этого изменения нужен только перезапуск ридера, текущий экспорт и аддон подходят.

## Подтверждение применения — 0.2.11

В ячейке «ПРИМЕНЕНО: ID» добавлена компактная чёрно-белая полоса: последние четыре публичных события `UNIT_SPELLCAST_SUCCEEDED` игрока. Каждая запись содержит последовательный номер, spellID и контрольную сумму. Скрытые/нечисловые ID не читаются и не кодируются. Полоса читается из того же кадра без OCR; одинаковые применения подряд различаются по номеру. Исходное поле последнего ID остаётся на экране.

Нужны `/reload`, новый `/ahw export` и загрузка этого экспорта в перезапущенный ридер. Новый экспорт содержит `castReceipt` с фактической геометрией и `castSpellIDs` (базовый ID и доступный override). Старый профиль продолжает работать, но подтверждение событий помечается `not_configured`; координаты новой полосы не угадываются.

События журнала:

- `key_sent`: Windows приняла пакет ввода.
- `action_response_observed`: изменился HUD; это прежняя эвристика ожидания.
- `player_cast_observed`: прочитано новое публичное событие игрока.
- `action_cast_observed`: после отправки наблюдалось событие с ожидаемым ID. Это подтверждает наблюдение применения, но не доказывает, что его вызвала именно программа, а не ручной ввод.
- `action_cast_unobserved`: за 2,5 с не удалось сопоставить событие либо чтение прервалось. Не является доказательством неудачного каста: возможны пропуск кольцевой истории, неизвестный override, скрытый ID или нечитаемая полоса.
- `cast_receipt_status`, `cast_receipt_gap`, `cast_receipt_reset`: состояние канала, пропуски событий и замеченный сброс после reload.

Проверка событий независима от управления: длительность нажатия, правила APL, ожидание GCD и повторы не изменены. На синтетических кадрах проверены чтение/контрольная сумма, повтор одинаковой способности, старое событие, несовпадающий ID, отсутствие повторного подтверждения и переход счётчика через максимум. Проверка в клиенте WoW ещё нужна.

Запуск на этом компьютере: двойной щелчок по `Start.vbs`.
Экспорт пользователя сохранён в `profile.json`: Arms, 27 индикаторов, 3840×2160, HUD слева.

1. Открой WoW с тем же HUD и разрешением. Перемещение HUD требует нового экспорта.
2. Нажми «Начать», вернись в WoW. Приложение читает экран только при активном окне игры.
3. Вернись в диагностику: при потере фокуса данные сбрасываются. Для одновременного наблюдения расположи окно на другом мониторе; не накрывай им HUD.
4. Выбор строки показывает область последнего доступного кадра. Цвета определяют состояние, OCR читает цифры. Пустые, обрезанные и неуверенные результаты — `?`, не ноль.

`state.json` — последний снимок для будущего оверлея. Потребитель обязан проверять `valid` и `expiresAt` (Unix time в секундах). Число в `value` — результат OCR, не гарантированное значение игры; рядом доступны исходный текст и уверенность. `colorConfidence` — мера близости цвета, не вероятность корректности. Автоматического определения перемещения HUD нет: при неизменном размере экрана нужен повторный импорт вручную.

Цвета опрашиваются отдельным потоком с целевым интервалом 100 мс; фактическая частота зависит от захвата и диска. Цветовой снимок действителен 0,8 с. OCR обрабатывает только последний доступный кадр без очереди старых изображений. Каждый элемент `numbers` имеет собственные `capturedAt` и `expiresAt` (1–5 с в зависимости от частоты поля): их тоже обязательно проверять. При изменении цветового состояния квадрата его старые числа сбрасываются. При потере фокуса опубликованный кеш OCR очищается. Это не гарантирует свежесть числа внутри непрерывно активного баффа: учитывай возраст наблюдения.

Распознавание идёт напрямую по областям текста, без поиска надписей на общем изображении. Цифры стаков нормализуются в чёрный текст на белом фоне; пустые области остаются неизвестными. Для старых экспортов цвет GCD берётся из палитры виджета 0.2.1; новые экспорты содержат отдельное поле `display.gcdColors`.

В версии аддона 0.2.3 десятичные значения форматируются непосредственно через `FontString:SetFormattedText("%.1f", value)`, без возврата к длинному исходному числу при ошибке. Таймерам назначен белый текст. Считыватель также поддерживает цветные цифры таймеров, вычитая цвет фона. Для отклонённых чисел применяется второй проход по исходному сглаженному изображению с отступами. Порог остаётся 0,92: буква O не заменяется нулём, расходящиеся числовые варианты отклоняются. В журнал добавлены `preprocess`, `variants` и причина принятия/отклонения. Заряды на зелёном фоне читаются как тёмный текст.

## Назначение клавиш в диагностике

В основной таблице добавлена колонка **«Клавиша»**. Дважды щёлкни по строке способности, нажми **«Записать клавишу»**, затем игровое сочетание и **«Сохранить»**. Кнопка **«Назначение клавиш»** сверху открывает общий список текущих способностей. Доступны Ctrl / Alt / Shift, функциональные клавиши, цифровой блок и отдельный выбор средней/боковых кнопок мыши. Esc отменяет запись; сочетания с Win не поддерживаются.

Назначения относятся к spell ID, поэтому перестановка квадратов не меняет привязку. Баффы, проки, дебаффы и ресурсы не имеют самостоятельных кнопок применения. «Героический удар» использует назначение «Мощного удара» через alias из экспорта. Повторяющееся сочетание для разных способностей блокируется с указанием конфликта. Запись клавиши действует только в сфокусированном поле редактора.

Файл для Arms: `reader/bindings/spec-71.json`. Сохранение атомарное; предыдущая версия сохраняется в `spec-71.json.bak`. JSON содержит `schema: AHelperW.Bindings`, `version: 1`, `specID`, `keyFormat: windows-vk`, словарь `bindings` по spell ID и `aliases`. Клавиатурная запись: `device: keyboard`, `vk` и упорядоченный список `modifiers`; мышь: `device: mouse`, `button: middle|x1|x2` и модификаторы. Пустое назначение — `null`. Левый и правый модификаторы считаются одинаковыми; основной Enter и Num Enter пока не разделяются.

Укажи те сочетания, которые уже назначены в WoW. OCR работает независимо, а остановка чтения не стирает назначения из таблицы. Открытие редактора останавливает исполнение; после сохранения нажми «Начать» снова. F8 зарезервирована для остановки и не назначается способностям.

## Исполнение APL (аддон 0.2.8)

### Оптимизация потока, этап 1 — захват области HUD

Ридер использует [MSS](https://github.com/BoboTiG/python-mss), закреплённую зависимость `mss==10.2.0`, для захвата только прямоугольника HUD. Прежний Pillow на Windows захватывал экран целиком, затем обрезал изображение. Экземпляр захвата живёт в потоке цвета; каждый кадр копирует собственные пиксели, поэтому следующий захват не меняет изображение у OCR. При ошибке MSS поток переходит на Pillow, сохраняя `captureFallbackError` в состоянии. Ошибки обоих способов обрабатываются обычной паузой ридера.

`pipeline.json` задаёт `captureBackend` (`mss` / `pillow`) и `colorIntervalMs` (по умолчанию 50, 20 Гц). Реальная частота ограничена временем всей обработки и загрузкой машины. OCR просыпается по сигналу нового кадра и берёт последний доступный кадр; очередь старых кадров не накапливается. Частота OCR отдельных полей не изменена. Аддон по-прежнему обновляет основные индикаторы своим тикером — ускорение ридера не увеличивает частоту обновления данных игры.

Замер на рабочем столе, 30 кадров одинаковой области 593×714: Pillow — медиана 81,34 мс / p95 87,17 мс, MSS — 4,16 мс / p95 5,26 мс. Данные: `logs/capture-benchmark-stage1.json`. Это микрозамер захвата, **не ускорение всего цикла в бою**. Проверены синтаксис Python, RGB/размер кадра, независимость пикселей первого кадра от следующего захвата и переход на Pillow при искусственной ошибке MSS. В проверках не отправлялись клавиши.

Для следующей записи боя добавлены `timings`: захват, разбор цветов, проверки фокуса, сверка пикселей/слияние OCR, APL/отправка, возраст кадра при решении и интервал между кадрами. OCR отдельно записывает время подготовки, основного и повторного распознавания, возраст кадра на входе и возраст результата. `capturedAt` теперь ставится **до захвата**, чтобы время самого захвата не скрывалось из возраста наблюдения.

APL, очереди нажатий, повторы, правила подсчёта целей и тайминги аддона на этом этапе не изменены. Новый экспорт или `/reload` для этой оптимизации не требуется. Полный выигрыш и корректность цветов в игре оцениваются по следующему логу.

При загрузке текущего профиля разбор APL и талантов прошёл инициализацию (`apl_model_loaded`). Активная героическая ветка определяется по узлу выбора: выданные базовые таланты неактивной ветки не включаются в условия APL. Исполнение клавиш и новые индикаторы аддона ещё требуют проверки в игре.

### Автооценка целей — 0.2.9

Обновление **0.2.10** добавляет в правый верхний угол ячейки целей отдельный цветной индикатор причины. Его координаты экспортируются как `context.targetCountStatus`, фиксированная палитра — `targetCounting.statusColors`. Текущий локальный профиль адаптирован; копия сохранена в `profile-before-0.2.10.json`. Нужен `/reload`; при изменении геометрии нужен новый экспорт.

В каждом `capture_result` и опубликованном состоянии есть `targetCountDiagnostic`: `sourceStatus` / `sourceLabel` — ответ аддона, `value` — актуальное число, `ocrReason` — состояние его распознавания. При изменении этих полей пишется отдельное событие `target_count_changed`. Причины источника: `stabilizing`, `no_nameplates`, `no_melee_observation`, `range_unknown`, `unit_unknown`, `waiting`; положительные состояния — `estimate` и `manual`. Неопознанный цвет — `unknown`, отсутствие области в старом экспорте — `unavailable`. Эти два случая не выдаются за причину из аддона.

Причина показывается в таблице ридера и строке статуса APL. Дополнительный индикатор читается по цвету и не требует OCR. Правила подсчёта и задержки стабилизации не изменены; эффективность будущих исправлений оценивается после записи с этим индикатором.

После `/reload` новый режим аддона по умолчанию — авто. `/ahw targets auto` или ПКМ по ячейке целей возвращает его после ручного режима. В ридере выбрать **«Из HUD»**: значения 1 / 2 / 3+ в выпадающем списке по-прежнему принудительно задают ручной режим.

HUD считает видимые живые враждебные неймплейты с положительной проверкой дистанции «Смертельного удара». Заголовок `ЦЕЛИ:~АВТО` обозначает оценку. Число не ограничено тремя; APL использует его для своих условий. Опрос — каждые 0,2 с, стабилизация роста — 0,4 с, уменьшения — 0,8 с. При смене числа до стабилизации, недоступных проверках либо отсутствии наблюдаемых ближних врагов показывается `?`, а не ноль. Чтение числа ридером назначено каждые 0,2 с; старое OCR-значение используется только при совпадении пикселей с текущим кадром и синем фоне действительного числа.

**Ограничения:** это оценка ближних видимых врагов, не точный радиус/сектор AoE и не список исключительно участвующих в бою целей. Проверка на манекенах показала доступные в бою враждебность и дистанцию MS, но признак боя самих манекенов всегда был false. Изменение камеры/настроек неймплейтов может менять оценку. Подземелья и рейды пока не проверены. При исчезновении части неймплейтов положительное число может недооценивать врагов; сглаживание этого не устраняет.

Геометрия HUD не изменена, текущий экспорт подходит. Новый экспорт дополнительно содержит описание `targetCounting`. Назначения клавиш сохранены. Прогноз TTD по-прежнему неизвестен без ручного ввода; режим манекена с долгим боем пока не реализован. Автооценка также не даёт HP остальных врагов для правил `target_if` — эти правила сохраняют прежнюю блокировку при нехватке данных.

1. Выполни `/reload` после установки аддона. Для перенесённого/изменённого HUD импортируй новый `/ahw export`: нужны новые области `inputAllowed` и `targetInterrupt`. Текущий профиль на этом компьютере адаптирован без изменения положения HUD.
2. Назначь игровые клавиши в колонке «Клавиша». Пустое назначение исключает действие из исполнения. Текущий список — способности из HUD; предметы и зелья в этом редакторе пока не представлены.
3. Выбери число целей: «Из HUD» использует ручную ячейку аддона, а 1 / 2 / 3+ — явное ручное значение в ридере. Фаза «По HP цели» использует прочитанный процент; ручные варианты задают условие фазы казни, не подменяя сам процент HP.
4. Включи «Автонажатия по APL», нажми «Начать» и переключись в WoW с выбранной враждебной целью. После получения достоверных данных может начать бой. Снятая галочка оставляет только диагностику. Сам запуск программы не начинает чтение или нажатия.
5. **F8 — остановить**. Кнопка «Остановить» делает то же самое. При потере фокуса WoW отправка приостанавливается; возвращение в WoW возобновляет работу запущенного цикла.

`apl.py` разбирает сохранённые выражения SimulationCraft из `docs/arms-apl/build-requirements.json`, сохраняя порядок действий, логические/арифметические операторы, переменные, вызовы списков и ветки Slayer. Таланты заново декодируются из текущего экспорта по таблице той же сборки; неподдерживаемый спек, героическая ветка или версия дерева блокируют запуск APL. Это не универсальный интерпретатор всех специализаций.

Неизвестное условие более приоритетного доступного действия блокирует выбор вместо перехода к менее приоритетной кнопке. Неточное/пустое/устаревшее число не считается нулём. Вспомогательные строки `auto_attack`, внешнее применение Power Infusion и симуляционные действия не отправляют клавиш; основная атака запускается обычным применением способности. Неназначенные действия, включая предметы и зелья, не исполняются. Выбор цели `target_if` для нескольких врагов и точная `movement.distance` остаются неизвестными; если от них зависит доступное действие, окно показывает причину остановки. Полное воспроизведение симулятора не заявляется.

Для отправки нужна свежая картинка, активное окно WoW, известная живая враждебная цель, готовый GCD и отсутствие мешающего каста. Малый индикатор в ячейке времени боя показывает разрешение ввода: открытый игровой ввод текста, меню, смерть или неизвестное состояние закрывают отправку. Метка прерываемости каста цели передаётся отдельным цветовым полем. Процент HP цели форматируется нативно после масштабирования кривой, без арифметики Lua над секретом. Эти новые сигналы требуют проверки в клиенте.

`input_sender.py` использует Windows SendInput и пары нажатие/отпускание. Фокус проверяется непосредственно перед отправкой; удерживаемые пользователем модификаторы и назначенная клавиша приостанавливают отправку. После отправки ожидается изменение HUD; без отклика новая оценка разрешается через 1,2 с. Изменение HUD не выдаётся за доказательство успешного применения. Ошибка отправки останавливает цикл. Нет очереди будущих нажатий или спама каждый кадр; точное игровое окно очереди заклинаний не моделируется.

В JSON-состоянии `execution` содержит результат решения. Журнал включает `apl_model_loaded`, `apl_decision`, `key_sent`, `action_response_observed`, `action_unconfirmed`, ошибки запуска и исполнения. Строка APL в окне объясняет ожидание или действие. Кнопка «Начать» фиксирует назначения/настройки до следующего запуска. Проверка боем и нажатиями в этом обновлении ещё не выполнялась.

## Дебаг-журнал

Запись включена автоматически. Каждый запуск создаёт отдельный `logs/<UTC-время>-<ID>.jsonl`. Одна строка — одно событие: профиль целиком, запуск/остановка чтения, каждый результат захвата, публикация состояния, паузы и ошибки со стеком. Результат содержит все прочитанные цвета/RGB, уверенность, OCR-текст, числа и время захвата. Даже кадры, отброшенные как устаревшие, сохраняются в событии `capture_result`. Повторяющиеся ошибки не подавляются. Журналы не удаляются и могут расти при длительном запуске; ошибка записи отображается в окне.

`ocr_result` отдельно фиксирует длительность распознавания, исходное время кадра, обновлённые в этом пакете числовые поля и факт принятия результата в кеш. `capture_result` фиксирует быстрый цветовой кадр и доступные на тот момент числа из кеша.

`last_success.json` хранит последний принятый успешный снимок и не затирается при потере фокуса или остановке. Это история (`historical: true`), а не текущее состояние. Проверяй `profileHash` и время внутри `observation`, особенно после смены профиля. Для диагностики после боя достаточно файлов, скриншоты не обязательны.

С версии 0.2.4 в `logs/<session>-crops/` сохраняются исходный квадрат способности на КД, его область таймера и JSON с результатом OCR. Лимит — три образца на квадрат за запуск, с интервалом не меньше пяти секунд. Это позволяет отличить пустой HUD от промаха области чтения.

Аддон 0.2.4 привязывает обычные КД через `GetSpellCooldownDuration(id, true)` → `SetCooldownFromDurationObject`, а перезарядку зарядов — через `GetSpellChargeDuration`. Числовой `SetCooldown` оставлен только для несекретных данных старого API. `/ahw timerdebug` показывает путь привязки и ошибки; диагностическое состояние сохраняется также в `AHelperWDB.timerDiagnostics`. `bound` означает успешный вызов setter, но не гарантирует, что цифры видимы: это подтверждают фрагменты.

В 0.2.5 таймеры квадратов подняты выше счётчиков. Экспорт содержит `display.timerLayout = "split-v1"` и новые области `timerRegion`; старые области центра не подходят. Текущий `profile.json` автоматически адаптирован под новую разметку при неизменном положении HUD, исходник сохранён рядом как `profile-before-0.2.5.json`. Обязательно `/reload` перед чтением.

Публикация теперь выполняется в отдельном потоке `StateWriter`, а не в callback Tk. Временные ошибки записи (включая блокировку файла читателем Windows) журналируются как `state_write_error` и повторяются с последним доступным кадром. Событие `state_published` пишется только после успешного `os.replace`. При остановке/смене профиля поколение исключает запись старых кадров. Отдельный контроль истечения срока очищает устаревший state даже при остановке поступления кадров. Исключения UI пишутся как `ui_error`; callback обновления планируется заново в `finally`. Очередь UI ограничена, промежуточные события могут пропускаться в таблице, но полные результаты остаются в журнале.

Таймеры и стаки распознаются независимо; пустой счётчик не означает один стак. Контекст считывается как числа и цветовые поля: названия кастов и текст автоатаки не распознаются. Неактивные/закрытые квадраты могут быть неоднозначны. HDR, цветовые фильтры и перекрытие HUD другими окнами требуют сверки. Покрытие и ограничения исполнителя описаны выше.

Окно изначально не запускает захват. Полные кадры остаются в памяти; на диск попадают JSON и ограниченный набор фрагментов HUD для диагностики таймеров.

## OCR 0.2.6

`ocr_policy.json` задаёт режим `optimized` (по умолчанию) или `full`, лимит областей на пакет и необязательные интервалы `periodSeconds` по ключам из `numbers`. Изменения применяются при загрузке профиля/перезапуске. Интервалы — минимальное время между попытками, не обещанная задержка: реальная частота зависит от длительности распознавания и числа активных областей.

- Ярость, заряды и стаки: интервал 0,15 с; таймеры: 0,6 с; служебные числа: 0,5–2 с. Пакет содержит до 12 новых областей, возможен второй проход для отклонённых результатов.
- Пустые счётчики обычных способностей и нестакающихся аур Arms исключены. Стаки «Размашистых ударов» и «Вихря клинков» берутся из соответствующего квадрата ауры (`sourceKey`, `derived`), если он есть в профиле.
- Словесные статусы дистанции, аксессуаров и зелья не отправляются в числовую OCR-модель. Их отключение не означает, что эти условия больше не нужны для APL. Причина пропуска находится в `reason`; неизвестное не превращается в ноль.
- При точном совпадении пикселей области используется результат прошлого чтения (`reusedPixels`), не дольше 10 с до повторного OCR. `capturedAt` относится к свежему кадру, `recognizedAt` — к исходному распознаванию. Устаревшие числа по-прежнему исключаются по `expiresAt`.
- В `ocr_result.stats` записываются `modelCrops`, `retryCrops`, `pixelCacheHits`, `fieldsUpdated`; событие `reading_started` содержит весь план чтения.
- Заряды способностей в аддоне теперь белые на чёрной подложке (`display.chargeText = "white-on-black"`), включая «Превосходство». Новый экспорт включает доступный `maxCharges` и `stackAuraID`. Цифры выше известного максимума отклоняются. Для заряжаемых способностей сохраняются также небольшие PNG счётчиков.

Текущий профиль адаптирован при неизменной геометрии HUD; резервная копия — `profile-before-0.2.6.json`. После обновления аддона нужен `/reload`. Прирост скорости и чтение зарядов 0/1/2 нужно оценить по новой записи боя; до неё ускорение не измерено.

## Исправления 0.2.7

Метки `Д`, `×`, `?` перенесены вниз ближе к центру квадрата. Они отделены от области таймера, счётчика зарядов справа и точки чтения цвета слева. Экспорт отмечает раскладку как `display.stateLabelLayout = "bottom-center-v1"`; геометрия областей OCR не меняется. Чёрная подложка зарядов расширена с запасом на округление пикселей.

Для белых счётчиков зарядов на чёрной подложке цветовой поток сверяет пиксели области с кадром, из которого получен OCR. Изменение цвета способности больше не сбрасывает число, если пиксели счётчика совпадают и срок `expiresAt` не истёк. `pixelValidatedAt` записывает время этой сверки; `recognizedAt` и `capturedAt` остаются исходными. При изменении цифр результат становится неизвестным (`charge_pixels_changed`) до нового чтения: предыдущий заряд не выдаётся за текущий. Смена фокуса по-прежнему очищает опубликованные данные. Для аур и старого оформления зарядов сохраняется проверка версии цветового состояния.

Изменения 0.2.7 требуют `/reload`. При неизменном положении HUD текущий профиль подходит; копия до обновления — `profile-before-0.2.7.json`. Проверка в игре пока ожидается: расходовать/восстанавливать заряды и менять дистанцию до цели, затем сравнить частоту `charge_pixels_changed` с прежними сбросами и чтение таймера «Рывка».

Перенос на другой ПК (Windows, Python 3.12 с Tk):

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\pythonw.exe reader.py
```
